# FlagPole

**Traffic control plans from pole sheets.** FlagPole drafts Traffic Control Plans (TCPs) from
electrical utility design drawings. (The code package is still named `tcp_auto`.)

Upload a PDF drawing where work is labeled **Construct** / **Remove**. Then confirm the road on a
map and enter the details the drawing doesn't have. FlagPole lays out a draft plan (signs, taper,
buffer, cones/drums, arrow board, flaggers, police officer, trucks) using the MUTCD plus Arizona and
East Valley city rules. Adjust it by drag-and-drop, then download a short PDF report (map,
explanation, timeline) or an Outlook email draft to send to the city or county.

> Generated plans are **drafts**. They must be reviewed and approved by qualified personnel before use.

- Plan and design decisions: [docs/PLAN.md](docs/PLAN.md)
- What each city's rules say, with citations: [docs/jurisdiction-research.md](docs/jurisdiction-research.md)
- Rule files and the source document register: [rules/](rules/README.md)

## Brand

- **Name:** FlagPole. The utility pole is the work; the flagger's flag is the traffic control.
- **Logo:** `frontend/logo.svg`. A white utility pole with an orange flag and cone on a blue tile. Works down to 16 px (also used as the favicon).
- **Colors:** blue is the interface (primary `#0a5cad`, navy `#0b2545`, bright `#1f7ae0`, tint `#eef5fd`).
  **Orange is reserved for work-zone devices** (cones, signs, work area) so it never competes with buttons on the map.
  This is an original palette in the spirit of Arizona utilities' blues. It doesn't copy any company's branding.
- Design tokens live at the top of `frontend/style.css`. The report uses the same palette (`backend/tcp_auto/report/templates/report.html`).

## Online demo (GitHub Pages)

A static demo with three sample projects runs on any phone or computer with no server. It's built from the real app: the plans, reports and checklists are generated by the backend at build time.

- **What works:** the editor, OSM map, dragging devices with live compliance checks, report and checklist previews and PDFs, the email draft, and the rules library.
- **What doesn't:** uploading new drawings, generating new plans, AI drafting and rule review need the full app. The demo says so when you try them.
- **Saving:** nothing is saved; reloading resets the demo.

**Publish:**
1. In the repo, go to Settings → Pages → Build and deployment → Source and choose **GitHub Actions**. Pages on a private repository needs a paid GitHub plan.
2. Run **Publish online demo** from the Actions tab, or push to `main`. The site appears at `https://<owner>.github.io/<repo>/`.

**Build locally:** `python packaging/build_demo.py site/`, then `python -m http.server -d site 8000`. The output is plain static files, so any static host works (Netlify, S3, an internal web server).

## Desktop app (Windows / Linux)

FlagPole can be packaged as a desktop app with PyInstaller. Double-click it and it starts on your
computer and opens in your browser.

**Using it**
- **Windows:** unzip `FlagPole-windows.zip` and run `FlagPole\FlagPole.exe`, or run the single-file `FlagPole.exe`.
- **Linux:** `tar -xzf FlagPole-linux.tar.gz && ./FlagPole/FlagPole`, or run the single-file `FlagPole`.
- A console window shows the address (default `http://localhost:8765/`). Closing it stops FlagPole.
- Projects, drawings and accepted rules are saved per user: `%APPDATA%\FlagPole` on Windows, `~/.local/share/flagpole` on Linux.
- PDF export uses the computer's **Microsoft Edge** (always on Windows) or **Google Chrome/Chromium**. If neither is found, use Preview and your browser's Print → Save as PDF, or set `TCP_CHROMIUM` to the browser's path.
- Options: `FlagPole --port 9000`, `--no-browser`, `--data-dir D:\FlagPoleData`, and `--host 0.0.0.0` to share on the office network. If you share it, set `TCP_ACCESS_KEY` too.

**Building it** (build on the OS you want the app for; PyInstaller doesn't cross-compile)

| | Folder build (faster start) | Single file |
|---|---|---|
| Windows (PowerShell) | `powershell -ExecutionPolicy Bypass -File packaging\build.ps1` → `dist\FlagPole\FlagPole.exe` + zip | `... build.ps1 -OneFile` → `dist\FlagPole.exe` |
| Linux | `packaging/build.sh` → `dist/FlagPole/FlagPole` + tar.gz | `ONEFILE=1 packaging/build.sh` → `dist/FlagPole` |
| Manually | `pip install ./backend pyinstaller && pyinstaller flagpole.spec` | `FLAGPOLE_ONEFILE=1 pyinstaller flagpole.spec` |

Or run the **Build desktop app** GitHub Action (`.github/workflows/build-desktop.yml`), either manually or by pushing a `v*` tag. It builds both platforms and attaches the files as artifacts.

The spec (`flagpole.spec`) bundles the frontend, rules, report templates and Python dependencies. It leaves out Playwright and PyMuPDF's optional AI layout model to keep the app small: on Linux about 130 MB for the folder build and about 60 MB for the single file.

## Run from source

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -e "backend[dev]"
flagpole                       # same launcher as the desktop app (or: python -m tcp_auto)
# developers: cd backend && uvicorn tcp_auto.api.app:app --reload   (data in backend/data)
```

Try it with the synthetic sample drawing in `samples/sample_drawing.pdf` (regenerate it with
`python samples/make_sample_drawing.py samples/sample_drawing.pdf`).

**Workflow in the app:**
1. **Drawing:** upload the PDF and check the found items.
2. **Details:** pick the city and road owner, describe the work, and set the timeline and contacts.
3. **Road:** use "Set work location", then "Draw road centerline" (or "Look up road (OSM)"). Confirm the speed and lanes, and add intersections.
4. **Plan:** generate the plan, then drag devices, add or delete them, and watch the checks.
5. **Report:** preview it, download the PDF, or download an email draft.

## Configuration

| Variable | Purpose | Default |
|---|---|---|
| `TCP_DATA_DIR` | Where projects, drawings, and accepted rules are stored | desktop app: per-user folder; `uvicorn` dev: `backend/data` |
| `TCP_RULES_DIR` | Jurisdiction rule files | `rules/` |
| `TCP_ACCESS_KEY` | If set, users need `/?key=<value>` once (cookie) to use the app | unset (open) |
| `TCP_TILE_URL` / `TCP_TILE_ATTRIBUTION` | Map tiles. Use a hosted provider in production (OSM's public tiles don't allow heavy use) | OSM standard tiles |
| `TCP_OVERPASS_URL`, `TCP_NOMINATIM_URL` | Map data services | public OSM endpoints |
| `TCP_CHROMIUM` | Path to Chrome/Edge/Chromium for PDF export | auto-detected |
| `TCP_PDF_ENGINE` | `auto` (Playwright, then installed browser) or `browser` (installed browser only) | `auto` |
| `TCP_LLM_PROVIDER` | `anthropic`, `openai_compatible`, or `azure_openai` (see [AI providers](#ai-providers)) | from AI settings |
| `TCP_LLM_BASE_URL` / `TCP_LLM_MODEL` / `TCP_LLM_API_KEY` | Endpoint, model, key for rule drafting | from AI settings |
| `TCP_LLM_DEPLOYMENT` / `TCP_LLM_API_VERSION` | Azure OpenAI deployment and API version | — / `2024-10-21` |
| `TCP_LLM_JSON_MODE`, `TCP_LLM_TIMEOUT`, `TCP_LLM_MAX_OUTPUT_TOKENS` | Output mode (`auto`, `json_schema`, `json_object`, `prompt`), timeout (s), output limit | `auto`, `180`, provider default |
| `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_ENDPOINT` | Standard variables, used when no key/endpoint is set | unset |

## Updating rules

Open **Rules** in the top bar:
- **Library:** every rules layer (federal, state, county, city) and what it contains, with citations and whether each rule is verified.
- **Propose a change:** pick a jurisdiction (or add a new city or county) and enter the source document title. Then either paste the manual's text and click **Draft with AI**, or write the rule manually from a template.
- **Review:** each change shows the current and proposed values, the supporting quote and any validation problems. The reviewer can edit, then **accept** or **reject**. Ticking "I checked every change against the source document" marks the rules verified; otherwise they show "confirm with agency".

Accepted rules are written to `<TCP_DATA_DIR>/rules_local/` as an overlay on the shipped `rules/` files, with a `changelog.jsonl`. That overlay is shared by everyone using the same FlagPole server; a database comes later for multi-server setups. A verified trigger replaces an unverified one with the same condition.

The AI only drafts. Every value goes through the same validator as manual entries, and nothing reaches the planner until it's accepted. Drafting sends the pasted text, never drawings, to whichever AI provider is configured.

## AI providers

FlagPole doesn't depend on any one AI vendor. It needs one thing from a model: "read this text and return JSON in this shape." Set the provider in **Rules → AI settings**, which has presets and a **Test connection** button, or with environment variables on the server. Environment variables take priority, which is handy when IT manages the server.

| Provider type | Works with | Settings |
|---|---|---|
| `anthropic` | Anthropic Claude API, or a company gateway in front of it | API key; model (default `claude-opus-5-5`); optional gateway URL |
| `openai_compatible` | OpenAI, Google Gemini (OpenAI endpoint), Mistral, Groq, OpenRouter, Together; **self-hosted / on-prem**: Ollama, vLLM, LM Studio, LocalAI, TGI; **gateways**: LiteLLM, Kong, Apigee. A gateway can front AWS Bedrock, Vertex AI and others | Endpoint URL (ending in `/v1`), model name, API key (often none for local servers) |
| `azure_openai` | Azure OpenAI Service | Resource URL, deployment name, API version, API key |

Examples:

```bash
# Company runs Ollama or vLLM on an internal server (nothing leaves the network)
TCP_LLM_PROVIDER=openai_compatible TCP_LLM_BASE_URL=http://llm.internal:11434/v1 TCP_LLM_MODEL=<model> flagpole

# Azure OpenAI
TCP_LLM_PROVIDER=azure_openai AZURE_OPENAI_ENDPOINT=https://acme.openai.azure.com \
  TCP_LLM_DEPLOYMENT=<deployment> AZURE_OPENAI_API_KEY=... flagpole

# AWS Bedrock (or anything else) through a LiteLLM gateway
TCP_LLM_PROVIDER=openai_compatible TCP_LLM_BASE_URL=https://litellm.corp/v1 TCP_LLM_MODEL=<gateway model name> TCP_LLM_API_KEY=... flagpole

# Anthropic
TCP_LLM_PROVIDER=anthropic ANTHROPIC_API_KEY=... flagpole
```

Notes:
- **JSON output:** with `auto`, FlagPole tries strict JSON-schema output first, then JSON mode, then plain instructions. It remembers what each server supports, so older or local models still work. Whatever comes back is checked by the same rule validator.
- **Gateway headers:** extra HTTP headers (for example a team or routing header) can be added under AI settings → Advanced.
- **Proxies:** corporate proxies set with `HTTPS_PROXY` / `NO_PROXY` are honored.
- **Model choice:** larger models produce better drafts. Small local models may need the "Instructions only" JSON mode and more reviewer edits.
- **Anthropic:** uses the official SDK with server-side refusal fallback (`fallbacks: "default"`).

## Deploy

`Dockerfile` builds a single container (API, frontend, rules, Chromium for PDFs). Mount a volume
at `/data`. This suits Azure Container Apps or App Service in a project-owned account
(see docs/PLAN.md §5.1).

## Layout

```
backend/tcp_auto/
  ingest/      PDF -> text spans, scale, excluded regions (title block, notes)
  extract/     Construct/Remove keyword extraction (keywords.yaml is editable)
  site/        OpenStreetMap road lookup and geocoding
  rules/       rule loader/resolver/evaluator (reads rules/*.yaml)
  timeline/    night detection, peak-hour and work-hour checks
  layout/      template selection and device placement
  compliance/  checks shared by the generator and the editor
  report/      narrative, SVG plan drawing, HTML/PDF report
  email/       .eml draft builder
  api/         FastAPI app (serves frontend/)
frontend/      editor (Leaflet, no build step; Leaflet vendored)
rules/         jurisdiction rules (YAML) + source register
samples/       synthetic sample drawing
```
